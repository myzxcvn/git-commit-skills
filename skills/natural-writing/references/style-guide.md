# 自然写作：文体与编辑规则

本文件是 `natural-writing` 的补充材料。具体用户要求始终优先于通用风格。

## 通用取舍

文字是否自然，取决于它有没有传达作者真实的判断，而不取决于是否使用口语词。

- 先回答“读者需要知道什么”，再决定标题和段落。
- 保留必要限定：适用于什么条件、依赖哪些假设、哪些结果尚未验证。
- 优先描述观察到的行为与因果链，而不是抽象价值判断。
- 允许用“但”“所以”“比如”等普通连接词；不为避免 AI 味而过度删减逻辑衔接。
- 不机械禁止“首先”“其次”：当材料确有顺序、步骤或层级时可以使用。
- 不为了句式多样性破坏术语的一致性。

## 技术方案与架构设计

推荐结构是：问题与目标 → 关键设计 → 取舍及边界 → 落地条件。根据篇幅灵活裁剪，不要求每篇都有全部章节。

一个可用的工程技术段落通常说明：

1. 采用什么做法；
2. 为什么这样设计；
3. 换来的成本或限制；
4. 在哪些场景下该设计会失效或需要调整。

例如，不写“通过引入事件驱动机制，可以有效提升系统的解耦性与扩展性”；
而写“让中断只负责采集和投递事件，业务模块在主循环处理消息。这样可以缩短中断路径，但事件队列需要明确容量、溢出和优先级策略”。

## README、API 与操作文档

- 开头说明项目解决什么问题，以及最小可用示例。
- 使用命令、路径、输入与输出要可验证；没有验证过就说“示例”，不声称已运行。
- 重要限制放在使用者需要做决定的位置，不要藏在文末套话中。
- 优先写“启动时读取配置”“失败后返回错误码”，少写“提供完整、强大、灵活的能力”。
- API 名、类型、命令和参数值必须准确。

## 技术博客

- 以一个真实存在的技术问题或明确的问题设定切入，不虚构作者经历。
- 分析原因时写出可复核的证据链；没有实测数据就注明是理论分析或预期。
- 可以有观点，但区分“我倾向于”“从接口设计看”“测试已证实”。
- 面向专业读者时避免把常识解释成长篇背景。

## 工作汇报

优先覆盖结果、影响、阻塞和下一步，但不硬套“四段式”。
尽可能使用可验证的范围和状态：

- “已合入接口重构，新增 6 个回归用例”优于“持续推进研发能力建设”。
- “待确认设备 A 的异常日志是否来自串口丢包”优于“仍存在一些挑战”。

当缺少事实或指标，不要擅自编造百分比、日期、项目里程碑。

## 日常沟通

- 保留交流对象所需的上下文，省去公文式开场。
- 用短句表达请求、解释或回应，语气礼貌但不必叠加客套。
- 不把微信消息改成会议纪要，也不要把正式邮件改成网络口语。

## 学术与规范文本

- 自然不等于口语化：保留定义、证据、引用与不确定性。
- 专业限定词（“可能”“在……条件下”“尚缺乏证据”）不能随意删去。
- 有格式规范时优先遵守，不为避免结构化而取消结构。

## 高频反模式及处理

| 反模式 | 编辑方法 |
| --- | --- |
| “在当今快速发展的时代……” | 删除，直接写问题 |
| “这是一个非常值得关注的话题。” | 删除，直接给信息 |
| “首先、其次、最后”套用到任意问题 | 按真实因果与重点排列 |
| “不仅……而且……并且……” | 拆开或只保留最重要的一层 |
| “显著提升、全面赋能、高效协同” | 说清具体指标、机制或使用场景 |
| 每段末尾重复一句总结 | 合并并删除重复结论 |
| 所有段落长度相同 | 按信息量决定段落长短 |
| 为了像真人故意加错别字 | 不这样做，保持准确和可读 |

## 最终检查

尝试删掉每段第一句和最后一句中的套话；如果论证没有受损，就应该删掉。
然后确认删减没有丢失定义、证据、条件、结论和用户明确要求保留的信息。
