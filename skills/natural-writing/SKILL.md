# 自然写作（Natural Writing）

把准确的内容写得更自然，而不是用刻意的口语、错别字或伪造经历制造“人味”。
目标是让文本像真正理解主题的人写出来：观点明确、信息具体、语言有节奏，保留必要的专业性。

## 使用边界和优先级

1. 用户明确的用途、语气、长度、格式和项目写作规范优先。
2. 事实准确性和原文实质含义优先于文风；不能为了顺口而改变技术结论。
3. 仅在被要求撰写、润色或改写时介入正文；普通问答不主动重写用户文字。
4. 不编造第一手经历、测试数据、来源、引用、采访或未经证实的判断。
5. 不承诺绕过 AI 检测器；自然表达不能保证检测结果。

## 写作流程

### 1. 确定读者和文体

优先从已有上下文判断用途。未指明时，默认使用简洁、专业、自然的中文。

- 技术方案：结论、约束、推理、权衡、落地方式，避免套话和未经证实的优越性结论。
- README / API 文档：先说明能力与用法，再给条件、限制和可复制示例。
- 技术博客：从具体问题切入，展示分析过程，允许适度个人判断，但不冒充亲身经历。
- 工作汇报：突出结果、影响、风险和下一步，避免“赋能”“全面提升”等空泛措辞。
- 日常沟通：按对象调整礼貌程度，不用报告体语气。
- 学术内容：保留规范、限定词和出处，不为“自然”而牺牲严谨。

更细的文体规则见 [references/style-guide.md](references/style-guide.md)。

### 2. 抽取信息骨架

动笔前区分：
- **事实**：有来源、原文或可靠上下文支持的信息。
- **判断**：作者观点、推论与工程取舍；需要时标注前提。
- **待证实**：缺少依据的效果、数据、因果关系或绝对化描述。

先确定这段文字真正要回答的问题，再安排叙述顺序。通常从结论或具体问题开始，不强行铺垫背景。

### 3. 改写正文

遵循以下规则，而不是机械替换词语：

- **先说有用的话**：删除“这是一个非常重要的问题”“随着技术快速发展”等空转开头。
- **少用模板连接词**：不机械套用“首先—其次—最后”“值得注意的是”“综上所述”；确有顺序时可以保留。
- **保留自然节奏**：长短句混用，段落随论证复杂度变化，不制造刻意对仗与统一字数。
- **用具体解释替代抽象赞美**：说明怎么做、为什么、何时不适合，而不是“显著赋能”。
- **根据复杂度组织结构**：一句能说明白就不列清单；需要对比或操作步骤时，表格和列表仍然合适。
- **保持专业准确**：代码、API、参数、版本、单位、专有名词和安全限制不得随意简化。
- **给出真实取舍**：有条件地讨论优缺点和失败模式，不为显得全面而罗列无关风险。
- **不增加虚假细节**：不捏造“我们在线上验证”“我踩过这个坑”等经历；没有数据就不用百分比代替判断。
- **不故意降质**：不加错字、口癖、冗余或语法错误来模拟人类。

### 4. 压缩和复核

对最终内容做一次编辑性检查：

1. 首段是否直接进入主题？
2. 每一段有没有新信息、推理或必要过渡？
3. 有没有重复的结论、空泛形容词或机械分点？
4. 是否保留了原文事实、技术限定条件和重要细节？
5. 是否把推测说成事实、把计划说成已完成？
6. 是否符合读者、场景和用户指定的风格？

删掉不必要的总结；如果结论已经清楚，不必再加“总之”。

## 输出约定

- 用户仅要求“润色/改写”：直接给出可使用的全文，不附加冗长的改写思路。
- 用户要求“对照/解释修改”：提供关键变化和必要说明，不逐字解释所有改动。
- 用户要求“保留格式”：保留 Markdown 标题层级、代码块、列表编号、引用和链接的语义；不要改变代码行为。
- 信息不足且会影响准确性时，保留明确的不确定性，不自行补全为事实。
- 仅当用户明确要求多个版本时，提供多种风格；否则给出一个质量最好的版本。
