# Git 提交规范

根据实际改动撰写可追溯的提交消息，准确说明原因、结果和已执行的验证。
具体仓库的当前规则和用户明确要求优先。

## 判断任务范围

- 用户只要求生成、建议、评审或修改提交消息时，只输出消息或评审结果，不执行提交。
- 用户要求“提交”时，完成范围核对、必要验证和本地 commit；这不包含 push。
- 用户明确要求“推送”“推到 GitHub”或等价操作时，才推送指定仓库和分支。
  会话中已经提供的授权继续有效，不重复索要同一授权。
- 不把提交任务扩展为 PR 创建、合并、发布、分支删除或历史改写。
  这些操作遵守用户已授权范围和目标仓库规则。

## 先核对事实

1. 读取目标仓库及相关目录的 `AGENTS.md`，按需读取其中指向的提交、验证和分支规则。
   分支名称、构建工具和发布要求均以目标仓库为准。
2. 查看当前分支、工作树、暂存区和近期提交，理解改动及标签习惯：

   ```bash
   git status --short --branch
   git diff --stat
   git diff
   git diff --cached --stat
   git diff --cached
   git log -5 --format='%h %s'
   ```

   新仓库尚无提交时，跳过历史读取。另行检查任务涉及的未跟踪文件，
   因为 `git diff` 不显示它们。
3. 区分本任务改动、用户已有改动和无关暂存内容。按明确文件或 hunk 暂存，
   不用 `git add .` 或 `git add -A` 把不明范围一并提交。
   发现无关暂存内容时保留原状；仅在提交范围确实无法判断时询问。
4. 依据仓库规则和受影响内容运行必要验证。只采用当前候选实际执行的结果，
   不把计划、猜测或旧版本结果写成已验证。验证失败时保留证据，
   先解决本任务问题或报告阻塞，不通过改写消息掩盖失败。

## 提交消息

### 摘要行

格式为 `[标签] 简短摘要`，支持连续多个标签，例如 `[ui][api] 展示分页查询结果`。

- 必须以至少一个方括号标签开头，最后一个标签与摘要之间用一个空格。
- 使用动宾短语或祈使语气，例如“修复崩溃”“新增配置”。
  不写“修复了错误”“我修复了错误”。
- 尽量不超过 50 个字符。这是长度建议，不为满足数字牺牲必要语义。
- 末尾不加句号。
- 第一行不放 Bug 引用或问题追踪简写，例如 `Fixes #123`；关联信息放在页脚。
- 不使用“昨天”“近期”等主观相对时间。
- 不包含私有链接、个人信息、密码、API 密钥或其他敏感信息。

常用标签如下；按改动职责选择，并沿用目标仓库历史，不把列表当作封闭枚举：

```text
[build] [core] [api] [ui] [cli] [config]
[tests] [tools] [scripts] [deps] [docs]
```

### 正文

- 与摘要之间空一行。
- 解释原因与意图，并在有助于理解时说明行为变化，不只列出修改文件。
- 每行不超过 72 个字符。
- 摘要已经清楚表达改动时，省略正文。

### 页脚

页脚放在最后一段，与正文或摘要之间空一行。
建议先写 `Bug:` 或 `Fixed:`，再写 `Test:`。

| 页脚 | 用途 |
| --- | --- |
| `Bug: <issue-id>` | 关联问题，不表示自动关闭。 |
| `Fixed: <issue-id>` | 关联已修复问题；是否自动关闭取决于平台配置。 |
| `Test: <说明>` | 记录实际执行的验证命令、测试目标或场景。 |

- 多个 `Bug:` 或 `Fixed:` 分行书写。
- 使用团队约定的纯 issue ID，不粘贴完整 URL，不编造编号。
- 只有实际修复且满足该问题验收要求时才使用 `Fixed:`；
  仅关联、记录或尚待验证时使用 `Bug:`，不承诺平台一定自动关闭。
- 实际执行测试或验证时，用一个或多个 `Test:` 记录关键验证。
  不把失败、跳过或局部验证写成完整通过；需要记录时注明结果和边界。
- 无适用测试或未执行测试时，省略 `Test:`，不写 `Test: None`。
  若仓库要求的测试因环境无法执行，在交付说明中明确原因。

### 示例

仅修改文档且没有执行验证时：

```text
[docs] 完善项目级开发规则
```

以下命令仅演示格式，实际提交必须替换为本次确实执行的验证：

```text
[api][core] 支持按状态筛选任务

在分页前应用状态筛选，使返回条目和总数保持一致。

Test: python -m pytest tests/test_task_filters.py
Test: python -m pytest tests/test_task_pagination.py
```

关联问题时，将已确认的编号放在页脚；尖括号内容是待替换占位符：

```text
[core] 修复取消任务后的重复执行

取消任务后移除队列中的待执行项，避免工作线程再次处理。

Bug: <issue-id>
Test: <本次实际执行的验证及结果>
```

## 执行与交付

仅生成消息时，返回可直接使用的提交消息；缺失的事实应在代码块外说明，
不把占位符混入宣称可直接提交的最终消息。

执行提交时：

1. 核对最终暂存差异并运行 `git diff --cached --check`。
   确认提交不包含无关改动、生成结果或敏感内容。
2. 将多行消息写入临时文件，通过 `git commit -F <message-file>` 提交，
   保留真实换行。使用工具结构化参数或带引号的 heredoc 写文件，
   不把消息直接拼入可执行的 shell 字符串。
3. 用 `git log -1 --format=fuller --stat` 和 `git status --short --branch`
   核对实际提交及剩余改动，报告短 SHA、摘要、验证结果和必要限制。
   允许保留用户的无关未提交改动，不能为制造干净工作树而清理它们。
4. 仅在已授权推送时，核对 remote、分支和待推送提交范围，再执行普通 push。
   不自动 force push 或重写历史。推送被拒绝时先读取原因，
   不以强制推送绕过远端新增提交或分支保护。
5. 推送后确认远端分支 SHA 与本地候选一致；如有 CI，
   按该 SHA 检查到终态并报告结果。没有配置 CI 就明确说明，
   不把“push 成功”写成“CI 通过”。
