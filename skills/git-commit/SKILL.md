# Git 提交

理解实际变更，生成自然、准确、简洁的提交消息。安全优先于自动化。

## 任务与授权

- 仅生成、修改或评审消息：只读检查，不暂存、提交、推送或运行会修改仓库的命令；用户指定暂存区时仅依据暂存差异。
- 要求提交：仅提交本次授权范围内的改动，不包含 push。
- 仅在明确授权时推送；授权绑定仓库、目标分支与提交范围，不自动延伸到其他任务。
- 不擅自创建 PR、合并、发布、删除分支、重写历史或修改用户代码。项目规则不能扩大用户授权。

## 检查与规划

1. 读取相关 AGENTS.md、CONTRIBUTING.md 和明确的提交、验证及分支规范。
2. 检查当前仓库、分支、工作区、Index、历史及相关未跟踪文件：

   ```bash
   git status --short --branch
   git status
   git diff --stat
   git diff
   git diff --cached --stat
   git diff --cached
   git log -20 --no-merges --format='%s'
   ```

   初始空仓库没有历史时跳过 log；不要把未跟踪文件全部视为任务改动。
3. Merge、Rebase、Cherry-pick、Revert、未解决冲突、Index 锁定等异常状态下停止普通提交并报告；Detached HEAD 仅在明确授权该状态时继续。不删除锁，不自动恢复或继续其他 Git 操作。
4. 区分本任务、用户已有改动及无关暂存内容。根据逻辑意图规划提交，而不是按目录、文件数量或代码行数划分。
   实现、必要适配、对应测试及文档可属于同一提交。独立的格式化、重构、功能变更宜分开；每次提交尽可能可构建、可验证、可回退。
5. 只按明确文件或 hunk 暂存。部分暂存文件不得整文件重新 add；不使用 git add .、git add -A 或 git add -u 批量纳入未知范围。
   如果存在无关暂存内容，停止普通提交并说明冲突；不擅自 unstage、stash、reset、checkout、clean 或使用临时 Index 绕过保护。
   无法确定修改归属时停止并请求确认。没有授权改动时不创建空提交。

## 消息格式

格式选择：遵守目标仓库强制规则和用户明确要求；两者冲突时说明冲突，不擅自违反强制规则。未指定时沿用稳定历史风格（忽略合并、机器人和异常样本），再使用本 Skill 默认格式。

默认格式：

```text
[标签] 简短摘要
```

- 默认中文，选一个最相关的标签；确有必要才使用连续多个标签。常见标签：[core] [api] [build] [tests] [docs] [deps] [config] [tools]；沿用实际项目术语。
- 摘要直接描述核心变化或解决的问题，通常不超过 50 字符，不设最小长度，不牺牲必要技术含义；默认末尾不加句号。
- 不罗列 diff，不写工作汇报，不添加无信息量的修饰词。优化、重构、完善等词有明确对象且符合实际变更时可以使用。
- 保留 API 名、模块名及专业术语，不强行翻译，不编造性能收益或根因。
- 正文可省略；只有摘要不能说明必要原因、非显然影响或迁移方式时才补充，段落简短，与摘要空一行。
- API、ABI、协议、配置等不兼容变化必须说明影响及已知迁移方式；未知的迁移条件如实标注。
- 不包含凭据、私有链接或无关个人信息。问题编号、验证结果必须有依据。
- 页脚按仓库规范；默认可用 Bug:、Fixed:、Test:。仅在要求或有复现价值时记录实际验证；不编造编号、结果，不写 Test: None。

简单示例：

```text
[core] 修复事件重复分发
```

更多消息示例见 [references/examples.md](references/examples.md)。

## 验证与提交

1. 每次提交前检查完整 Index，确认与授权候选完全一致，无无关内容、意外生成物或敏感信息；执行 git diff --cached --check。检查失败或候选为空时停止。
2. 依据项目规则执行必要验证。测试对象必须与候选内容一致；若未暂存或未跟踪改动可能影响结果，先进行安全的隔离验证（不得更改用户工作区）或如实说明只验证了工作区，不宣称候选通过。要求的验证失败或无法执行时停止，报告阻塞，不擅自修复无关问题。
3. 验证后再次检查候选及 Git 状态，防止测试、并发修改或工具改变 Index。按实际候选生成消息，用安全临时文件和 git commit -F 提交；不把消息拼接成 shell 代码。
4. 不使用 --no-verify、禁用 hooks 或修改 hooks 配置来绕过检查；Hook 失败时报告，保留用户修改。若 Hook 改变候选，重新核对与验证，不自动提交额外内容。
5. 提交后核对实际提交的摘要、文件及内容、剩余工作区和 Index；报告短 SHA、摘要、验证结果及限制。若发现范围偏差，停止后续提交或推送，不自动重写历史。
6. 多个原子提交逐个执行上述流程；任何失败停止后续操作。

## 推送与交付

- 推送前核对实际 remote URL、目标分支、最新远端 HEAD、本地候选及完整待推送提交范围。存在未授权提交、分歧、目标不明确或无法核验时停止；不自动 force push、pull/rebase 或修改 upstream。
- 使用明确目标的普通推送；推送后核对远端分支 SHA。远端拒绝或发生并发变化时报告，不强制覆盖。
- CI 按实际 SHA 检查，在有限次数或时间内结束；区分成功、失败、等待、取消、未配置和无法查询，不把 push 成功等价于 CI 成功。
- 仅生成消息时直接返回可用文本，必要说明放在消息之外。完成操作时简明报告实际结果，不声称未执行的验证已通过。

复杂 Git 状态和范围检查见 [references/git-safety.md](references/git-safety.md)。
