# 文档写作（Document Writing）

把用户目标和可核实材料转化为**准确、可用、便于维护**的文档。
写作不是填满模板，而是帮助读者理解问题、做出决策或完成操作。

## 任务边界

- 用户要求新建文档：按照读者、用途、材料和交付位置创建；如未指定格式，优先 Markdown。
- 用户要求更新已有文档：先阅读原文和上下文，只修改相关内容，保留有效信息、链接、术语和既有风格。
- 用户仅要求提纲、评审或建议：不要擅自创建文件或修改仓库。
- 用户要求修改文档，不代表授权修改程序代码、提交、推送、创建 PR 或发布；严格遵守实际操作权限与既有授权。
- 对 Word、PDF 或其他格式的要求，使用当前环境可用的对应能力；不能生成时说明限制，不能把 Markdown 冒充成指定文件。
- 优先遵守用户指令、目标项目的 `AGENTS.md` / `CONTRIBUTING.md` / 文档规范及现有约定。

## 标准工作流

### 1. 明确文档契约

从用户请求和现有上下文提取：
- **目的**：说明、决策、操作、交付、审查还是归档？
- **读者**：工程师、维护者、评审者、管理者、普通用户？
- **范围**：系统、模块、版本、平台和不包含的内容。
- **产物**：文件路径、格式、语言、深度、模板或排版要求。
- **验收**：阅读后能回答哪些问题、完成哪些操作？

若这些信息足以开展工作，就直接执行，不为填写模板反复追问。无特殊约定时，以中文、Markdown、专业自然的表达为默认。

### 2. 查证资料，建立事实边界

面向现有项目时，优先查阅实际来源而不是凭记忆推断：
1. 阅读项目级规则、文档索引、现有相关文档及上下游设计。
2. 检查与主题有关的代码、接口声明、配置、构建脚本、测试和示例。
3. 识别实际实现、计划设计、历史方案、假设与待验证事项的区别。
4. 对需要时效性或外部证据的事实，优先核实权威来源，并保留来源或版本信息。
5. 不编造指标、测试结果、发布状态、引用、文件路径、命令输出、接口或实现细节。

信息不足时，明确标注“建议方案”“待确认”“尚未验证”，不要把假设写成已落地事实。不要未经核对就在文档中引用不存在的路径、符号或资源。

### 3. 选择合适的文档类型和结构

按读者任务选择结构，详见 [文档类型指南](references/document-types.md)。
根据需要参考 [可裁剪模板](references/templates.md)。

- **README / 快速开始**：项目是什么、运行条件、最短可执行路径、常见问题、限制。
- **技术方案 / 架构设计**：背景与目标、约束、备选方案、决策依据、模块与数据流、接口契约、异常边界、验证和演进。
- **API / 协议文档**：契约、参数、返回值、单位与范围、错误语义、并发/生命周期约束、兼容性、示例。
- **ADR / RFC**：问题与决策、候选方案、权衡、影响及状态，不把提案伪装为已采纳决定。
- **部署 / 排障手册**：前置条件、操作步骤、预期结果、失败定位、恢复/回滚与风险。
- **测试方案 / 项目报告**：目标、方法、证据、结论、限制和后续动作；区分计划、已执行和未完成。

简单文档不必硬套所有章节；复杂设计也不能因为追求简洁省略关键约束。

### 4. 从核心问题开始写

- 开头尽快告诉读者“解决什么问题”或“读完可以做什么”。
- 每节回答一个明确问题，按依赖关系排列，标题有信息量。
- 优先描述机制、条件、权衡和失败路径；少写空泛赞美和无根据的性能结论。
- 技术术语、命令、接口、默认值、时间单位、内存/线程/进程边界应前后一致。
- 使用示例必须区分“示意代码”和“已经验证可执行的代码”；依赖与平台条件写清楚。
- 只在确实提高可理解性时加入表格、流程图、时序图和代码片段。
- 架构图中的模块、链路、数据方向应与正文一致。需要图时优先使用项目支持的 Mermaid 或文字结构图，不凭空增加模块。
- 控制标题层级和列表深度；不要为每一段加结论，也不要为了“完整”重复介绍同一事实。

写作自然度可参考同仓库的 `natural-writing` 技能，但本技能应独立完成任务，不假设其他技能已经安装。

### 5. 按类型补齐关键工程信息

针对软件工程文档，按相关性检查以下要素，不适用则不写：
- **边界**：职责归属、依赖方向、进程/线程/MCU 与 SoC 分工。
- **契约**：输入输出、错误码、状态机、生命周期、权限和版本兼容。
- **实时性与资源**：容量、延迟预算、内存/Flash、阻塞风险、队列满或超时策略。
- **故障行为**：异常处理、超时、重试、降级、恢复、清理和可观测性。
- **落地路径**：最小可交付版本、迁移步骤、测试/验收标准、未决问题。

不要机械补充与项目无关的术语。对未能证实的性能或资源指标使用目标值/预算值标识。

### 6. 交付前检查

按 [文档质量清单](references/review-checklist.md) 检查：
- **准确性**：事实、代码/API、路径、命令、版本、数据是否有依据？
- **完整性**：目标读者能否独立完成主要任务或理解关键决策？
- **一致性**：术语、图、接口、表格、例子是否互相矛盾？
- **可执行性**：命令是否具有完整前提，是否实际运行过？
- **可维护性**：稳定的链接、明确的范围和版本、避免复制容易过时的信息？
- **安全性**：有无凭据、内部地址、敏感数据或危险操作缺少说明？

有可用工具时，检查 Markdown 格式、相对链接、示例语法与本次改动范围。没有执行验证就如实说明，不写“已验证通过”。

## 交付规则

- 用户要**文档正文**：直接交付完整内容。
- 用户要**仓库内文档**：按约定路径落盘；新建文件前检查是否存在，修改前读取现状，避免覆盖无关改动。
- 用户要**评审**：按影响程度报告事实错误、遗漏、歧义和改进建议；不要用主观风格偏好掩盖技术缺陷。
- 用户要**文档模板**：提供适合场景的可删减结构，并标注占位符。
- 交付时说明文件位置、本次覆盖范围及尚未验证项；不要宣称不存在的构建、测试或提交已完成。
- 除非用户另有要求，不额外生成 PPT/PDF/图像等衍生物。

## 示例调用

```text
使用 $document-writing，基于仓库实际代码编写 docs/architecture.md。
重点解释模块职责、数据流、接口边界、线程模型和错误处理。
不要修改程序代码；对未实现能力明确标注为规划。
```

```text
使用 $document-writing 为项目补全 README：
环境要求、构建命令、最小运行示例、配置项和常见问题。
逐项核对仓库中的文件路径和实际命令。
```

```text
使用 $document-writing 评审当前 API 文档。
优先找出契约缺失、示例错误、兼容性问题和歧义，暂不修改文件。
```
