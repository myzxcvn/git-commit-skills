# 文档类型选择指南

选择文档类型时，先问读者需要完成什么任务。不要在一个文档中重复覆盖全部细节；合理拆分并互相引用。

## README / 项目首页

**读者目标**：快速知道项目用途，并成功完成一次最小使用。

建议内容：
- 一句话定位及适用边界；
- 依赖、平台和版本要求；
- 获取、构建、运行的最短路径；
- 一个可复核的使用示例与预期行为；
- 配置位置、测试方式、限制以及后续文档链接。

验证重点：命令、路径、依赖条件真实存在；示例是否注明已测试或仅供参考。
不把整个架构设计复制进 README。

## 技术方案 / 架构设计

**读者目标**：知道为什么选择这个方案，能实现、评审、维护它。

根据问题复杂度选用：
- 背景、现状、痛点和成功标准；
- 目标、非目标、前提、资源与平台约束；
- 系统上下文、模块职责、依赖方向；
- 数据流、控制流、状态与生命周期；
- 核心接口及契约（输入、输出、错误、并发）；
- 候选方案与取舍；
- 故障处理、恢复、性能/内存预算及可观测性；
- 安全、兼容性和迁移策略；
- 验收、测试计划和未决问题。

审查重点：职责无重叠、依赖方向可控、异常路径完整；预算值不冒充测量值。

## API / 协议规范

**读者目标**：在不阅读实现的情况下正确调用或集成。

至少包括：
- 适用版本、传输方式、序列化或调用约定；
- 命名、类型、单位、范围、默认值；
- 前置条件、返回结果、错误码；
- 生命周期、线程安全、并发语义、时序与超时；
- 兼容性及变更策略；
- 最小示例、反例和边界条件。

二进制协议还应解释字节序、字段长度、帧界定、校验、重传、超时和未知字段处理。
不能仅以头文件的声明代替行为契约。

## ADR / RFC / 决策记录

**读者目标**：追踪决策的背景、选项、原因和影响。

- 标题、日期、状态（Proposed / Accepted / Superseded 等）；
- 背景、约束和待解决的问题；
- 候选方案及其利弊；
- 决策及理由；
- 影响、未决事项、后续验证。

不要把未批准提案写成已接受方案，或回填不存在的会议与决策人员。

## 操作手册 / 部署 / 排障

**读者目标**：安全完成任务，并在失败时恢复。

- 适用环境、前置条件与风险提示；
- 操作步骤（命令、参数、权限、目标设备）；
- 每一步的预期结果和检查方法；
- 常见失败、日志/诊断路径；
- 回滚与恢复、清理方法。

危险命令应说明影响范围；不能把破坏性操作包装成普通步骤。

## 测试方案 / 实验报告

**读者目标**：知道如何验证，以及证据支持什么结论。

- 目标、假设、环境、设备/软件版本；
- 指标定义、测量方法和样本条件；
- 测试步骤、通过阈值和数据记录格式；
- 实际结果、偏差、局限性和复现方式；
- 结论及下一步。

计划测试与实际结果分开写；没有执行测试不得虚构结果。

## 项目方案 / 阶段报告

**读者目标**：理解目标、范围、决策和推进状态。

- 背景、业务目标与交付范围；
- 里程碑、依赖、资源与风险；
- 关键决策和替代方案；
- 已完成、进行中、受阻事项；
- 验收标准和下一步责任。

数据、进度和承诺必须有来源，不能因缺少材料而自动补齐。

## 组合建议

- README 链接架构文档、API 文档和操作手册，而不是复制它们。
- 重大技术决策优先拆成 ADR，并在架构文档中引用。
- 设计草案与已实现行为分别标记；版本变化时同步更新使用手册。
