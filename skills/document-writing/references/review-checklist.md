# 文档交付质量清单

建议按“事实 → 可用 → 完整 → 表达”的顺序复核。未做的检查不要标记为通过。

## P0：必须检查

- [ ] 用户明确的目标、读者、范围和输出格式得到满足。
- [ ] 关键事实可追溯到用户材料、项目代码或可信外部来源。
- [ ] 已实现、建议设计、待开发、测试计划和实测结果被明确区分。
- [ ] API 名、文件路径、命令、配置字段、版本、单位与源码或权威文档一致。
- [ ] 未编造 benchmark、测量数据、测试结果、引用或个人经历。
- [ ] 不包含凭据、私有令牌、敏感内容或无必要的内部环境信息。
- [ ] 重大风险、关键前提和不可忽略的限制已经写明。

## P1：面向工程交付

- [ ] 每个模块/角色职责清晰，跨模块依赖和数据方向明确。
- [ ] 必要的前置条件、输入输出、错误语义、并发约束与生命周期完整。
- [ ] 对适用的超时、重试、容量溢出、故障恢复给出明确行为。
- [ ] 架构图、时序、代码示例与正文一致。
- [ ] 构建或操作步骤给出了适用平台和预期结果。
- [ ] 若为部署/运维文档，涉及状态改变的操作说明回滚或恢复方式。
- [ ] 验收标准可判断，未决问题有明确标识。

## P2：可读性和维护性

- [ ] 开头清楚说明主题、用途或结论。
- [ ] 标题层级合理，不把短文过度分段。
- [ ] 内容没有重复、口号式总结和不必要的模板套话。
- [ ] 首次出现的关键术语给出定义，后续用词一致。
- [ ] 表格、代码块、图和列表确实帮助读者理解。
- [ ] 相对链接和跨文档引用尽量使用稳定、可维护的路径。
- [ ] 大型文档中概览、决策、契约、操作步骤职责清楚，避免互相复制。

## 验证和交付记录

根据环境条件执行，而不是默认宣称已经执行：

1. 静态检查：Markdown 语法、围栏配对、空白及格式错误。
2. 链接检查：本地相对路径存在；外部链接在具备网络条件时抽样核验。
3. 示例检查：能运行时执行示例并记录结果；不能运行时注明缺失环境。
4. 改动检查：只涉及授权文件，不覆盖已有无关修改。
5. 交付说明：列出新增/修改的文件、内容范围及未验证项。

可以在目标项目支持时使用 `git diff --check` 或专用 lint 工具；
不要默认项目安装了 markdownlint、Mermaid 渲染器或代码运行环境。
